## 2. 예측 가능한 장애 시나리오

### 시나리오 1: 주문 생성 API 응답 지연

#### 증상
```
✅ Alert: P95 응답 시간 > 5초
✅ Grafana: DB Connection Pool 100% 사용
✅ Logs: "Connection is not available, request timed out"
```

#### 원인
- DB 연결 풀 고갈 (max-pool-size: 3)
- Slow Query 증가
- DB 락 경합

#### 1차 대응 (10분 이내)

```bash
# 1. 현재 상태 확인
kubectl logs -f deployment/ecommerce-app | grep "Connection"

# 2. 긴급 조치: 연결 풀 증설
kubectl set env deployment/ecommerce-app \
  SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE=20

# 3. 배포 확인
kubectl rollout status deployment/ecommerce-app

# 4. 모니터링
watch -n 1 'curl -s http://localhost:8080/actuator/health'
```

#### 2차 대응 (30분 이내)

```bash
# 1. Slow Query 확인
mysql> SHOW FULL PROCESSLIST;
mysql> SELECT * FROM information_schema.INNODB_TRX;

# 2. 인덱스 추가 (필요 시)
mysql> CREATE INDEX idx_orders_user_created
       ON orders(user_id, created_at DESC);

# 3. 리소스 증설 (필요 시)
kubectl scale deployment/ecommerce-app --replicas=3
```

#### 복구 확인

- [ ] P95 응답 시간 < 2초
- [ ] DB 연결 풀 사용률 < 60%
- [ ] Error Rate < 0.1%

#### 사후 조치

- [ ] Root Cause Analysis (RCA) 문서 작성
- [ ] DB 연결 풀 설정 영구 변경
- [ ] 부하 테스트 재수행

### 시나리오 2: 쿠폰 발급 대량 실패

#### 증상
```
✅ Alert: Coupon Issue Error Rate > 50%
✅ Grafana: Redis CPU 100%
✅ Logs: "RedisCommandTimeoutException"
```

#### 원인
- Redis 분산 락 타임아웃
- Redis CPU 과부하
- 쿠폰 선착순 이벤트로 트래픽 폭증

#### 1차 대응 (5분 이내)

```bash
# 1. Redis 상태 확인
redis-cli INFO stats
redis-cli SLOWLOG GET 10

# 2. Redis 재시작 (최후의 수단)
docker restart ecommerce-redis
# 또는
kubectl rollout restart deployment/redis

# 3. 비동기 발급 API로 트래픽 우회
# API Gateway에서 동기 API 차단
# 공지: "현재 쿠폰 발급이 지연되고 있습니다"
```

#### 2차 대응 (30분 이내)

```bash
# 1. Redis 리소스 증설
# redis.conf
maxmemory 4gb  # 2gb → 4gb
maxclients 20000  # 10000 → 20000

# 2. 분산 락 타임아웃 조정
kubectl set env deployment/ecommerce-app \
  LOCK_WAIT_TIME=5000 \
  LOCK_LEASE_TIME=10000

# 3. 실패한 쿠폰 요청 재처리
# Kafka에서 실패 이벤트 재발행
```

#### 복구 확인

- [ ] Redis CPU < 70%
- [ ] 쿠폰 발급 성공률 > 95%
- [ ] Lock Timeout Rate < 1%

### 시나리오 3: MySQL 마스터 다운

#### 증상
```
✅ Alert: MySQL Health Check Failed
✅ Grafana: DB Connection 0
✅ Logs: "Communications link failure"
```

#### 원인
- MySQL 프로세스 crash
- 디스크 풀
- 네트워크 장애

#### 1차 대응 (30분 이내) - 읽기 전용 모드

```bash
# 1. MySQL 상태 확인
systemctl status mysql
docker logs ecommerce-mysql

# 2. 긴급 조치: 읽기 전용 모드 전환
kubectl set env deployment/ecommerce-app \
  READ_ONLY_MODE=true

# 3. 주문/결제 API 차단
# API Gateway Circuit Breaker 활성화
# 공지: "현재 주문 접수가 일시 중단되었습니다"

# 4. Redis 캐시만으로 서비스
# 상품 조회, 랭킹 조회는 정상 작동
```

#### 2차 대응 (1시간 이내) - MySQL 복구

```bash
# Option A: MySQL 재시작
docker restart ecommerce-mysql

# Option B: 레플리카 → 마스터 승격
# 1. Replication Lag 확인
mysql> SHOW SLAVE STATUS\G

# 2. 레플리카를 마스터로 승격
mysql> STOP SLAVE;
mysql> RESET SLAVE ALL;

# 3. Application 설정 변경
kubectl set env deployment/ecommerce-app \
  SPRING_DATASOURCE_URL=jdbc:mysql://replica:3306/ecommerce

# 4. 읽기 전용 모드 해제
kubectl set env deployment/ecommerce-app READ_ONLY_MODE=false
```

#### 복구 확인

- [ ] MySQL Health Check 정상
- [ ] 주문 생성 API 정상
- [ ] 데이터 정합성 확인

#### 사후 조치

- [ ] MySQL 장애 원인 분석
- [ ] 백업 검증
- [ ] Replication 재구성

### 시나리오 4: Kafka 브로커 전체 다운

#### 증상
```
✅ Alert: Kafka Producer Send Failed
✅ Grafana: Kafka Consumer Lag 급증
✅ Logs: "TimeoutException: Topic ecommerce.order.events not present"
```

#### 원인
- Zookeeper 다운
- 디스크 풀
- 네트워크 파티션

#### 1차 대응 (1시간 이내) - Outbox 활용

```bash
# 1. Kafka 상태 확인
docker ps | grep kafka
docker logs ecommerce-kafka

# 2. 주문 완료는 정상 처리 (Outbox에 저장됨)
# Kafka 없이도 주문은 완료 가능
# 이벤트는 DB Outbox에 저장

# 3. Kafka 재시작
docker-compose restart kafka zookeeper

# 4. Outbox 이벤트 재발행
# OutboxEventDispatcher가 자동으로 PENDING 이벤트 재발행
# 수동 확인:
mysql> SELECT COUNT(*) FROM outbox_events WHERE status='PENDING';
```

#### 2차 대응 (2시간 이내) - Kafka 복구

```bash
# 1. Zookeeper 재시작
docker restart ecommerce-zookeeper

# 2. Kafka 브로커 재시작 (순차)
docker restart ecommerce-kafka-1
sleep 30
docker restart ecommerce-kafka-2
sleep 30
docker restart ecommerce-kafka-3

# 3. Topic 상태 확인
kafka-topics --bootstrap-server localhost:9092 --list
kafka-consumer-groups --bootstrap-server localhost:9092 --describe --group ranking-updater

# 4. Consumer Lag 모니터링
watch -n 5 'kafka-consumer-groups --bootstrap-server localhost:9092 --describe --all-groups'
```

#### 복구 확인

- [ ] Kafka 브로커 3개 모두 정상
- [ ] Consumer Lag < 100
- [ ] Outbox 이벤트 모두 SENT 상태

### 시나리오 5: Redis 메모리 부족

#### 증상
```
✅ Alert: Redis Memory > 95%
✅ Grafana: Cache Eviction Rate 급증
✅ Logs: "OOM command not allowed"
```

#### 원인
- 캐시 TTL 미설정
- Memory Leak
- 예상보다 높은 트래픽

#### 1차 대응 (15분 이내)

```bash
# 1. Redis 메모리 상태 확인
redis-cli INFO memory
redis-cli MEMORY STATS

# 2. 긴급 조치: 캐시 삭제
redis-cli FLUSHDB  # ⚠️ 주의: 모든 캐시 삭제

# 3. Eviction Policy 확인
redis-cli CONFIG GET maxmemory-policy
# 권장: allkeys-lru

# 4. 메모리 증설 (Docker)
docker update --memory=4g ecommerce-redis
```

#### 2차 대응 (1시간 이내)

```bash
# 1. 메모리 사용 패턴 분석
redis-cli --bigkeys
redis-cli --memkeys

# 2. TTL 미설정 키 찾기
redis-cli KEYS * | while read key; do
  ttl=$(redis-cli TTL $key)
  if [ $ttl -eq -1 ]; then
    echo "$key has no TTL"
  fi
done

# 3. 캐시 TTL 설정 추가 (코드)
# CacheConfig.java
@Bean
public RedisCacheConfiguration cacheConfiguration() {
    return RedisCacheConfiguration.defaultCacheConfig()
        .entryTtl(Duration.ofMinutes(10));  // 기본 TTL
}
```

### 시나리오 6: CPU 100% 지속

#### 증상
```
✅ Alert: CPU Usage > 95% (5분 지속)
✅ Grafana: Thread Count 급증
✅ Logs: 응답 없음
```

#### 원인
- 무한 루프 (버그)
- GC Thrashing (Heap 부족)
- 과도한 스레드 생성

#### 1차 대응 (5분 이내)

```bash
# 1. Thread Dump 수집 (재시작 전!)
kubectl exec -it pod/ecommerce-app-xxx -- jstack 1 > thread-dump.txt

# 2. Heap Dump 수집 (선택)
kubectl exec -it pod/ecommerce-app-xxx -- jmap -dump:format=b,file=/tmp/heap.hprof 1

# 3. 긴급 재시작
kubectl rollout restart deployment/ecommerce-app

# 4. 로드 밸런서에서 트래픽 차단 (일시)
kubectl scale deployment/ecommerce-app --replicas=0
sleep 10
kubectl scale deployment/ecommerce-app --replicas=3
```

#### 2차 대응 (1시간 이내)

```bash
# 1. Thread Dump 분석
# - 동일한 스택 트레이스 반복 → 무한 루프
# - "waiting on monitor" 다수 → Deadlock
# - GC 스레드 과다 → Heap 부족

# 2. Heap 증설 (필요 시)
kubectl set env deployment/ecommerce-app \
  JAVA_OPTS="-Xms4g -Xmx4g"

# 3. 버그 수정 후 재배포
```

## 4. 롤백 절차

### 4.1 Application 롤백

```bash
# 1. 이전 버전 확인
kubectl rollout history deployment/ecommerce-app

# 2. 롤백 실행
kubectl rollout undo deployment/ecommerce-app

# 3. 특정 버전으로 롤백
kubectl rollout undo deployment/ecommerce-app --to-revision=3

# 4. 롤백 확인
kubectl rollout status deployment/ecommerce-app
```

### 4.2 Database 롤백

```bash
# 1. 백업에서 복원 (최후의 수단!)
mysql -u root -p ecommerce < backup-2025-12-14.sql

# 2. 특정 시점 복원 (PITR)
# AWS RDS의 경우
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier ecommerce-db \
  --target-db-instance-identifier ecommerce-db-restored \
  --restore-time 2025-12-14T10:00:00Z
```
