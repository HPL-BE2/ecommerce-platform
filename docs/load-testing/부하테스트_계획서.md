**작성일**: 2025-12-14
**작성자**: 개발팀
**승인 요청 대상**: CTO, 인프라팀 리더

## 📋 Executive Summary

본 문서는 E-Commerce Platform의 **부하 테스트 계획**을 수립하여, 시스템의 성능 한계를 파악하고 안정적인 서비스 운영을 위한 기준을 마련하기 위해 작성되었습니다.

### 주요 목표
- ✅ **성능 기준선 확립**: 평시 및 피크 타임 처리 용량 측정
- ✅ **시스템 한계점 파악**: Breaking Point 도달 시점 파악
- ✅ **최적 배포 스펙 도출**: 비용 대비 최적 인프라 구성
- ✅ **장애 대응 체계 수립**: 병목 지점 개선 및 대응 매뉴얼 작성

## 1. 테스트 대상 선정

### 1.1 선정 기준

부하 테스트 대상은 다음 기준으로 선정하였습니다:

| 기준 | 가중치 | 설명 |
|------|--------|------|
| **비즈니스 중요도** | 40% | 매출 직결, 사용자 경험 핵심 |
| **기술적 복잡도** | 30% | 동시성 제어, 분산 시스템 패턴 |
| **예상 트래픽** | 20% | 일일 요청 수, 피크 타임 집중도 |
| **장애 영향도** | 10% | 장애 시 비즈니스 손실 규모 |

### 1.2 선정된 API 및 근거

#### 🥇 **1순위: 주문 생성 API** (`POST /api/v1/orders`)

**선정 이유:**
- ✅ **매출 직결**: 주문 실패 = 직접적인 매출 손실
- ✅ **최고 복잡도**: 재고 예약, 쿠폰 적용, 지갑 차감을 하나의 트랜잭션으로 처리
- ✅ **동시성 제어**: Redis 분산 락 + 낙관적 락 조합
- ✅ **보상 트랜잭션**: 실패 시 롤백 메커니즘 필요

**기술적 특징:**
- 병렬 검증: 재고, 쿠폰, 지갑 잔액
- 상품별 분산 락 획득 (순서 보장으로 Deadlock 방지)
- 낙관적 락 충돌 시 재시도 (최대 3회, 지수 백오프)
- Outbox 패턴으로 이벤트 발행

**예상 병목:**
- Redis 분산 락 대기 시간
- DB 연결 풀 부족
- 낙관적 락 충돌률

---

#### 🥈 **2순위: 쿠폰 발급 API (동기)** (`POST /coupons/{id}/issue`)

**선정 이유:**
- ✅ **선착순 이벤트**: 특가 행사 시 동시 접속자 폭증
- ✅ **Redis 분산 락**: 단일 쿠폰에 대한 동시 요청 제어
- ✅ **원자적 카운터**: Redis INCR로 발급 수량 관리
- ✅ **높은 동시성**: 수천 명이 동시에 버튼 클릭

**기술적 특징:**
- Lock wait time: 2초
- Lock lease time: 5초
- 한도 초과 시 즉시 DECR (보상)
- DB 트랜잭션 내 발급 내역 저장

**예상 병목:**
- 분산 락 경합 (Thundering Herd)
- Redis CPU 사용률 급증
- 락 타임아웃으로 인한 실패율 증가

---

#### 🥉 **3순위: 상품 목록 조회 API** (`GET /api/v1/products`)

**선정 이유:**
- ✅ **최대 트래픽**: 사용자가 가장 많이 호출
- ✅ **캐싱 효과 검증**: Redis 캐시 히트율 측정
- ✅ **읽기 성능 기준**: 시스템 전체 읽기 성능 지표

**기술적 특징:**
- Redis 캐시 우선 조회 (TTL: 3분)
- 커서 기반 페이징 (대용량 데이터 최적화)
- 캐시 미스 시 DB 조회 후 캐싱

**예상 병목:**
- 캐시 미스 시 DB 부하
- Redis 메모리 부족
- 네트워크 대역폭

---

#### 🎖️ **4순위: 지갑 충전 API** (`POST /api/v1/wallets/{userId}/topups`)

**선정 이유:**
- ✅ **결제 시스템 핵심**: 지갑 잔액 관리
- ✅ **비관적 락**: SELECT FOR UPDATE로 동시성 제어
- ✅ **멱등성 보장**: Idempotency-Key 검증

**기술적 특징:**
- DB 트랜잭션 내 비관적 락
- 오버플로우 방지 (Math.addExact)
- 거래 내역 추적

**예상 병목:**
- 비관적 락 대기 시간
- DB 연결 풀 부족

---

### 1.3 제외된 API 및 이유

| API | 제외 이유 |
|-----|----------|
| 상품 상세 조회 | 상품 목록 조회와 유사한 패턴 |
| 주문 완료 | 주문 생성 후 순차 호출 (별도 테스트 불필요) |
| 쿠폰 발급 (비동기) | Kafka 기반이라 부하 테스트 효과 제한적 |
| 상품 랭킹 조회 | Redis Sorted Set 조회만 (단순) |

## 2. 테스트 시나리오

### 2.1 시나리오 1: Baseline (평시 트래픽)

**목적**: 정상 운영 시 성능 기준 확립

| 항목 | 값 |
|------|-----|
| **Virtual Users** | 100명 |
| **Duration** | 5분 |
| **Ramp-up** | 30초 |
| **패턴** | Constant load |
| **API 비율** | 상품 조회 70%, 주문 생성 20%, 쿠폰 발급 10% |

**성공 기준:**
- P95 Latency < 500ms (읽기), < 1s (쓰기)
- 에러율 < 0.1%
- CPU 사용률 < 60%

---

### 2.2 시나리오 2: Peak Load (피크 타임)

**목적**: 특가 행사 시 트래픽 급증 대응 검증

| 항목 | 값 |
|------|-----|
| **Virtual Users** | 100 → 1000 (점진적) |
| **Duration** | 10분 |
| **Ramp-up** | 5분 |
| **패턴** | Ramping VUs |
| **API 비율** | 상품 조회 50%, 주문 생성 30%, 쿠폰 발급 20% |

**성공 기준:**
- P95 Latency < 1s (읽기), < 2s (쓰기)
- 에러율 < 1%
- TPS > 1000 req/s

---

### 2.3 시나리오 3: Stress Test (한계점 탐색)

**목적**: 시스템 Breaking Point 파악

| 항목 | 값 |
|------|-----|
| **Virtual Users** | 500 → 3000 (점진적) |
| **Duration** | 15분 |
| **증가 패턴** | 매 3분마다 500 VU 증가 |
| **패턴** | Stress testing |

**성공 기준:**
- Breaking Point 도달 시점 파악
- 장애 발생 후 복구 시간 측정
- 에러율 급증 시점 (> 5%) 기록

---

### 2.4 시나리오 4: Spike Test (DDoS 시뮬레이션)

**목적**: 급격한 트래픽 증가 대응력 검증

| 항목 | 값 |
|------|-----|
| **Virtual Users** | 100 → 2000 (30초 내) → 100 |
| **Duration** | 10분 |
| **Spike 지속** | 2분 |
| **패턴** | Spike testing |

**성공 기준:**
- Spike 중 에러율 < 5%
- Spike 후 정상 복구 시간 < 1분
- Circuit Breaker 정상 동작

## 3. 성능 목표 (SLA)

### 3.1 응답 시간 목표

| API | P50 | P95 | P99 | Max |
|-----|-----|-----|-----|-----|
| 상품 목록 조회 | < 100ms | < 300ms | < 500ms | < 1s |
| 상품 상세 조회 | < 50ms | < 150ms | < 300ms | < 500ms |
| 지갑 충전 | < 200ms | < 500ms | < 1s | < 2s |
| 주문 생성 | < 300ms | < 1s | < 2s | < 5s |
| 쿠폰 발급 (동기) | < 200ms | < 800ms | < 1.5s | < 3s |

### 3.2 처리량 목표

| 지표 | 목표 | 측정 방법 |
|------|------|----------|
| **Total TPS** | > 1000 req/s | k6 `http_reqs` |
| **주문 생성 TPS** | > 500 req/s | k6 custom metric |
| **쿠폰 발급 TPS** | > 200 req/s | k6 custom metric |

### 3.3 안정성 목표

| 지표 | 목표 | 측정 방법 |
|------|------|----------|
| **에러율** | < 0.1% (평시), < 1% (피크) | k6 `http_req_failed` |
| **가용성** | > 99.9% | Uptime monitoring |
| **데이터 정합성** | 100% | DB 검증 스크립트 |

| 프로파일 | CPU | Memory | 비고 |

| **baseline** | 2 Core | 2GB | 권장 최소 |

## 5. 테스트 도구: k6

### 5.1 k6 선정 이유

| 항목 | 설명 |
|------|------|
| **성능** | Go 언어 기반, 단일 머신에서 수만 VU 생성 |

| **비용** | 오픈소스 무료 |

### 5.2 k6 설치

```bash

brew install k6

# Docker
docker pull grafana/k6

# 실행 예시
k6 run load-tests/scenarios/01-product-list.js
```
