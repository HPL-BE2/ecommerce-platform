## 1. 병목 #1: DB 연결 풀 부족 🔴

### 1.1 증상

- **발생 시점**: VUs > 500
- **현상**:
  - Connection wait timeout 에러 급증
  - 응답 시간 P95 1s → 5s (5배 증가)
  - TPS 감소 (456 → 287 req/s)

### 1.2 원인 분석

**현재 설정:**
```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 3  # ❌ 너무 작음!
      minimum-idle: 3
      connection-timeout: 20000
```

**문제:**
- 최대 3개 연결로 수백 명의 동시 요청 처리 불가
- 대기 시간 증가 → 응답 지연 → 연결 점유 시간 증가 → 악순환

### 1.3 개선 방안

#### 즉시 적용 (Critical)

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20  # ✅ 3 → 20
      minimum-idle: 10       # ✅ 유휴 연결 유지
      connection-timeout: 30000
      idle-timeout: 600000
      max-lifetime: 1800000
```

**계산 근거:**
```
권장 Pool Size = (Core 수 * 2) + Effective Spindle 수
                = (4 * 2) + 5
                = 13 ~ 20
```

#### 예상 효과

| 지표 | 개선 전 | 개선 후 | 개선율 |
|------|---------|---------|--------|
| P95 Latency | 5,000ms | 1,200ms | 76% ⬇️ |
| TPS | 287 | 450+ | 57% ⬆️ |
| Connection Wait | 70% | < 5% | 93% ⬇️ |

## 2. 병목 #2: 낙관적 락 충돌 🟡

### 2.1 증상

**재고 예약 실패율:**
- VUs 100: 2%
- VUs 500: 8%
- VUs 1000: 25% ❌

**재시도 폭증:**
- 평균 재시도 횟수: 1회 → 2.7회
- 최대 재시도 실패: 3회 도달 → 주문 실패

### 2.2 원인 분석

**현재 코드:**
```java
// InventoryPersistenceAdapter.java
@Retry(maxAttempts = 3, backoff = @Backoff(delay = 100, multiplier = 2))
public void reserve(long productId, int qty) {
    InventoryEntity inventory = repo.findById(productId).orElseThrow();

    if (inventory.getStock() < qty) {
        throw new InsufficientStockException();
    }

    inventory.setStock(inventory.getStock() - qty);
    inventory.setVersion(inventory.getVersion() + 1);  // 낙관적 락

    repo.save(inventory);  // version 충돌 시 예외
}
```

**문제:**
- 동시 요청 시 version 충돌 빈번
- 재시도 간격이 짧음 (100ms → 200ms → 400ms)
- 3회 재시도 후 실패 → 사용자 경험 악화

### 2.3 개선 방안

#### Option A: 재시도 로직 개선 (즉시 적용 가능)

```java
@Retry(
    maxAttempts = 5,  // 3 → 5회
    backoff = @Backoff(
        delay = 200,     // 100 → 200ms
        multiplier = 2.5,  // 2 → 2.5
        maxDelay = 3000    // 최대 3초
    )
)
```

**기대 효과:**
- 충돌률 25% → 8%
- 재시도 성공률 75% → 92%

#### Option B: 분산 락 타임아웃 증가 (단기)

```java
@DistributedLock(
    key = "#productId",
    waitTime = 5,   // 2 → 5초
    leaseTime = 10  // 5 → 10초
)
```

**기대 효과:**
- 락 획득 성공률 향상
- 동시 업데이트 횟수 감소

#### Option C: Lock-Free 알고리즘 (장기)

```java
// Redis Lua Script 활용
String script = """
    local stock = redis.call('GET', KEYS[1])
    if tonumber(stock) >= tonumber(ARGV[1]) then
        redis.call('DECRBY', KEYS[1], ARGV[1])
        return 1
    else
        return 0
    end
    """;
```

**장점:**
- 원자적 연산으로 충돌 제로
- 재시도 불필요

**단점:**
- 개발 복잡도 증가
- DB-Redis 동기화 필요

## 3. 병목 #3: Redis 분산 락 대기 시간 🟡

### 3.1 증상

- **Lock Wait Timeout**: 2.5% (1000 VUs)
- **평균 대기 시간**: 500ms
- **최대 대기 시간**: 1,800ms

### 3.2 원인 분석

**상품별 순차 락 획득:**
```java
for (OrderItem item : items) {
    lock.acquire(item.productId);  // 순차 획득
    // ... 재고 예약
    lock.release(item.productId);
}
```

**문제:**
- 여러 상품 주문 시 순차 처리 → 시간 누적
- 다른 요청의 락 대기 → Cascading Delay

### 3.3 개선 방안

#### Option A: 락 타임아웃 조정 (즉시)

```java
@DistributedLock(
    waitTime = 5,   // 2 → 5초 ✅
    leaseTime = 10  // 5 → 10초 ✅
)
```

#### Option B: 배치 락 획득 (단기)

```java
// 모든 상품 ID를 정렬하여 한 번에 획득
List<Long> productIds = items.stream()
    .map(OrderItem::getProductId)
    .sorted()  // Deadlock 방지
    .collect(Collectors.toList());

multiLock.acquire(productIds);  // 배치 획득
// ... 재고 예약
multiLock.release(productIds);
```

**기대 효과:**
- 락 획득 시간 50% 단축
- Timeout 률 2.5% → < 0.5%

## 4. 병목 #4: Kafka Producer 동기 발행 🟢

### 4.1 증상

- 주문 완료 API P99: 923ms
- Kafka send() 평균 소요: 120ms
- 전체 응답 시간의 13% 차지

### 4.2 원인 분석

**현재 코드:**
```java
kafkaTemplate.send("ecommerce.order.events", event).get();  // ❌ 동기 대기
```

**문제:**
- `.get()` 호출로 ACK 대기
- acks=all 설정으로 모든 브로커 응답 대기

### 4.3 개선 방안

#### Option A: 비동기 발행 (즉시)

```java
kafkaTemplate.send("ecommerce.order.events", event)
    .whenComplete((result, ex) -> {
        if (ex != null) {
            log.error("Kafka send failed", ex);
            // Fallback: Outbox에 기록
        }
    });
```

**기대 효과:**
- 응답 시간 923ms → 800ms (13% 개선)

#### Option B: Kafka 설정 최적화 (단기)

```yaml
spring:
  kafka:
    producer:
      acks: 1  # all → 1 (leader만 확인)
      batch-size: 32768  # 16384 → 32KB
      linger-ms: 10  # 0 → 10ms (배치 대기)
      compression-type: snappy
```

**Trade-off:**
- 메시지 손실 가능성 미세 증가
- 처리량 2배 향상

## 5. 추가 개선 사항

### 5.1 인덱스 최적화

**Slow Query 발견:**
```sql
SELECT * FROM orders
WHERE user_id = ? AND created_at > ?
ORDER BY created_at DESC;

-- 실행 시간: 87ms (목표: < 10ms)
```

**개선:**
```sql
CREATE INDEX idx_orders_user_created
ON orders(user_id, created_at DESC);
```

**예상 효과:**
- Query 시간 87ms → 8ms (91% 개선)

### 5.2 Connection Pool Warmup

**문제:**
- 서버 시작 직후 첫 요청 느림 (Cold Start)
- 연결 생성에 100~200ms 소요

**개선:**
```yaml
spring:
  datasource:
    hikari:
      initialization-fail-timeout: -1  # 시작 시 풀 생성
```

### 5.3 Cache Warming

**문제:**
- 서버 재시작 후 캐시 미스율 100%
- 처음 몇 분간 DB 부하 증가

**개선:**
```java
@EventListener(ApplicationReadyEvent.class)
public void warmupCache() {
    // 인기 상품 100개 미리 캐싱
    topProducts.forEach(product -> {
        productService.getProductDetail(product.getId());
    });
}
```
